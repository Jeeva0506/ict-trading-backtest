FIX DETAILS:

BUG 1 — ACCOUNT_RULES NameError (CRITICAL → FIXED)
  File: live/mt5_connector.py, line 1756
  Problem: Code used `ACCOUNT_RULES['starting_balance']` but ACCOUNT_RULES
           was NEVER imported or defined. Every time a position closes via
           broker SL/TP hit, _manage_positions() throws NameError. This
           propagates to the main loop's except handler, incrementing
           consecutive errors. After 5 closes, the bot stops entirely.
  Fix: Replaced `ACCOUNT_RULES['starting_balance']` with `ACCOUNT_SIZE`
       (already imported from config_fundednext.py).
  Impact: Without fix, the bot would crash after the next trade closes.

BUG 2 — SL protection $6000 hardcoded fallback (HIGH → FIXED)
  File: live/sl_protection.py, line 724
  Problem: When mt5.account_info() returns None, the position monitor
           uses hardcoded $6000 as account_balance. If the account grows
           or is a $100K funded account, the calculated max_loss would be
           ~$117 instead of ~$1950, causing premature emergency closes.
  Fix: Reads ACCOUNT_SIZE from environment variable with $6000 fallback.
  Impact: Prevents erroneous emergency closes on funded accounts.

BUG 3 — Weekly report on Saturday (HIGH → FIXED)
  File: live/trade_journal.py, line 636
  Problem: Weekly report scheduled for Saturday 8 AM (weekday==5), but
           the watchdog stops the bot during weekends. Report never fires.
  Fix: Changed to Friday 8 PM (weekday==4, hour==20) — bot is still active.

BUG 4 — Watchdog file handle leak (HIGH → FIXED)
  File: watchdog.py, line 191
  Problem: start_bot() opens stdout/stderr file handles for the subprocess
           but never closes the previous handles on restart. Each restart
           leaks 2 file descriptors. After ~500 restarts → OSError.
  Fix: Close existing handles before opening new ones.

BUG 5 — SL protection logger outside guard (HIGH → FIXED)
  File: live/sl_protection.py, line 452
  Problem: `logger.error(traceback.format_exc())` was outside the
           `if logger:` guard. If logger is None, crashes with
           AttributeError during SL verification exception handling.
  Fix: Moved inside the `if logger:` block.

BUG 6 — max_trades_per_day fallback (MEDIUM → FIXED)
  File: live/mt5_connector.py, line 1360
  Problem: `FUNDEDNEXT_RULES.get("max_trades_per_day", 3)` uses fallback
           3 if key is missing. Config value is 2. If key were ever removed,
           the bot would take 3 trades/day instead of 2.
  Fix: Changed fallback from 3 to 2.

BUG 7 — MFE/MAE=0 treated as empty (MEDIUM → FIXED)
  File: live/trade_journal.py, line 297
  Problem: `if mfe_pts and risk_pts` — when mfe_pts==0 (legitimate value),
           Python treats 0 as falsy, writing '' instead of '0.0R'. Trades
           that never moved favorably lose this data point.
  Fix: Changed to explicit `if mfe_pts is not None and mfe_pts != ''`.

BUG 8 — Report scheduler silent failure (MEDIUM → FIXED)
  File: live/mt5_connector.py, line 2363
  Problem: Bare `except: pass` silently swallows report errors. If
           journal Excel is corrupted or locked, daily/weekly reports
           fail with zero visibility.
  Fix: Changed to `except Exception as e: logger.warning(...)`.

BUG 9 — SL protection bare except (MEDIUM → FIXED)
  File: live/sl_protection.py, line 457
  Problem: Bare `except:` catches SystemExit/KeyboardInterrupt, preventing
           graceful shutdown during SL verification failures.
  Fix: Changed to `except Exception:`.

BUG 10 — SESSION_CLOSE missing journal columns (MEDIUM → FIXED)
  File: live/mt5_connector.py, line 1922
  Problem: The force-close (SESSION_CLOSE) path in _manage_positions
           didn't pass the new journal columns (drawdown, commission,
           swap, risk_tier, point_value, lots). These were only in the
           SL/TP close path, creating incomplete journal entries.
  Fix: Added DD%, commission, swap, risk_tier, point_value, lots to
       the SESSION_CLOSE close_trade() call.

SECTION 2: LIVE vs BACKTEST — EDGE-AFFECTING DIFFERENCES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are ARCHITECTURAL differences between live and backtest that
systematically affect trade count, win rate, and PnL. They are NOT bugs
— most are intentional risk controls. But they explain why live results
will differ from backtest expectations.

┌────┬──────────────────────────────┬──────────────┬─────────────────────┐
│ #  │ Difference                   │ Affects      │ Direction           │
├────┼──────────────────────────────┼──────────────┼─────────────────────┤
│ 1  │ 10-second polling vs M1 bars │ MFE tracking │ LIVE WORSE          │
│ 2  │ BE = entry+0.5×spread        │ BE exits     │ LIVE SLIGHTLY BETTER│
│ 3  │ 1-2s random order delay      │ Fill quality │ LIVE WORSE          │
│ 4  │ MIN R guard (3/5 pts)        │ Trade count  │ LIVE FEWER TRADES   │
│ 5  │ SPREAD-TO-R guard (30%)      │ Trade count  │ LIVE FEWER TRADES   │
│ 6  │ POST-FILL risk guard (1.5×R) │ Trade count  │ LIVE FEWER TRADES   │
│ 7  │ News filter (5min/15min)     │ Trade count  │ LIVE FEWER TRADES   │
│ 8  │ Daily cap = 2 trades         │ Trade count  │ LIVE FEWER TRADES   │
│ 9  │ Stale signal guard (15 bars) │ Trade count  │ LIVE FEWER TRADES   │
│10  │ Max SL cap = 80 pts          │ Trade filter │ LIVE FEWER TRADES   │
│11  │ Execution slippage (real)    │ PnL          │ LIVE WORSE          │
│12  │ Real spread costs            │ PnL          │ LIVE WORSE          │
└────┴──────────────────────────────┴──────────────┴─────────────────────┘

DETAIL ON EACH:

#1 — 10-second polling vs M1 bar granularity
  Backtest: Sees every M1 bar's high/low. MFE is the TRUE intra-bar peak.
  Live: Checks every 10 seconds using bid/ask. A 20-second spike that
        retraces is captured by backtest but missed by live polling.
  Effect: Live trailing SL is LESS aggressive (underestimates MFE by 
          missing spikes) → live may exit at lower levels OR let trades
          run too far. Net effect: unpredictable but slightly worse live WR.
  Magnitude: ~1-3% win rate difference over long term.

#2 — BE level: entry + 0.5×spread vs exact entry
  Backtest: SL moves to exactly entry price at 1R.
  Live: SL moves to entry + half spread (buy) or entry - half spread (sell).
  Effect: Live BE exits are slightly profitable ($1-3 per trade), while
          backtest BE exits are exactly $0.
  Magnitude: Tiny positive (< $50/month).

#3 — 1-2 second random order delay
  Purpose: Prop-firm detection avoidance (prevents pattern recognition
           of instant order execution at signal time).
  Effect: Price moves 0.5-2 points during the delay, worsening the fill.
  Magnitude: ~$10-30/trade negative impact. Over 10 trades/month = 
             $100-300/month drag.

#4 — MIN R guard (rejects R < 3 pts SPX/US2000, R < 5 pts others)
  Purpose: Tiny-R signals have spread+slippage eating most of the risk
           budget, guaranteeing > 1R losses on losing trades.
  Backtest: Takes all signals regardless of R-size. 16yr report shows
            311 signals filtered by min R (77% of all skipped signals).
  Live: Rejects these signals.
  Effect: ~20% fewer trades on some symbols. BUT the filtered trades
          were mostly losers, so live edge may be BETTER.

#5 — SPREAD-TO-R guard (rejects if spread > 30% of R)
  Purpose: When spread eats > 30% of R, the trade has no edge even if
           it wins (net profit too small to overcome losing trades).
  Backtest: Models fixed spread per trade. Doesn't account for variable
            spreads during news/low-liquidity.
  Live: Dynamically checks real-time spread. Rejects high-spread moments.
  Effect: Filters ~2-5 trades/month. Usually high-spread = around news
          = higher chance of adverse fill.

#6 — POST-FILL risk guard (closes if actual R > 1.5× designed R)
  Purpose: If fill price drifts so far from signal that the SL distance
           is 50%+ larger than planned, the risk budget is blown.
  Backtest: Uses signal entry price = fill price (no slippage).
  Live: Can slip 0.5-5 points on fill, occasionally making actual R
          much larger than designed.
  Effect: Very rare (< 1 trade/month). But when triggered, prevents
          what would be a 2-3× oversized loss.

#7 — News filter blocks (5min before, 15min after high-impact)
  Purpose: FundedNext accounts must not be exposed to NFP/FOMC/CPI news
           risk. A single spike can breach daily DD limit.
  Backtest: No news filter. Takes all signals including during news.
  Live: Blocks signals near FOMC, NFP, CPI, etc.
  Effect: Filters ~2-4 trades/month. The 16yr backtest would show
          some of these as big winners (news breakouts). Live misses them.
  Note: This is CORRECT for prop-firm survival but means live edge
        is artificially lower than backtest on news-heavy weeks.

#8 — Daily cap of 2 trades across all symbols
  Purpose: Limits correlated loss clusters. On a bad day with 3 losing
           trades, that's 3 × 1.5% = 4.5% daily DD (near the 3% limit).
  Backtest: Each symbol runs independently. Can take 5 trades/day
            (1 per symbol × 5 symbols) with no cross-symbol limit.
  Live: Max 2 trades/day total across all symbols.
  Effect: On days when 3+ symbols have valid signals, live takes the
          first 2 and skips the rest. At 6 trades/week (backtest), this
          is rarely hit. But during high-volatility weeks, it clips
          ~1-2 additional trades.

#9 — Stale signal guard (rejects if entry is > 15 bars old)
  Purpose: Prevents re-entering old signals after bot restart or
           news filter lift. A 15-minute-old signal may have already
           exhausted its edge.
  Backtest: Always enters at the exact signal bar. No staleness.
  Live: If the signal was generated 15+ bars ago (due to news block,
        reconnection, or slow cycle), it's rejected.
  Effect: Filters ~1-3 trades/month, especially after news windows.

#10 — Max SL cap = 80 points
  Strategy default: max_sl = 10,000 (effectively unlimited).
  Live override: max_sl = 80.0 points.
  Effect: Wide-ORB setups with > 80pt SL are filtered in live but taken
          in backtest. GER30 has the most impact (ORB ranges 50-120 pts).
  Note: This is MATCHED with the MT5 3-year backtest (which also uses 80).
        But the original strategy allows larger SLs in theory.

#1 — Telegram auth bypass (HIGH — NOT FIXED — requires user decision)
  File: live/telegram_commands.py, line 155
  Issue: If `authorized_users` list is empty, `is_authorized()` returns
         True for ANY Telegram user. Anyone who discovers the bot's token
         can send /emergency and close all positions.
  Recommendation: Add your Telegram user ID to the authorized_users list
         in the config. Or change default behavior to deny-all when
         the list is empty.

#2 — No Excel file locking (HIGH — structural, needs openpyxl lock)
  File: live/trade_journal.py
  Issue: add_trade() and close_trade() both call load_workbook()/save().
         If two trades are journaled in the same 10-second cycle (e.g.,
         two positions close simultaneously), one save overwrites the
         other. Also throws PermissionError if the file is open in Excel.
  Mitigation: Current single-threaded main loop makes simultaneous
         journal writes extremely rare. Real fix would be a threading
         lock around all journal operations.

#3 — News filter fails open (MEDIUM — architectural trade-off)
  File: live/news_filter.py, line 97
  Issue: If API fails AND disk cache is stale (>6h), fetch_news() returns
         empty list → is_news_time() returns False → trades proceed.
  Mitigation: Disk cache persists across restarts. API failures for 6+
         consecutive hours are rare. For a prop firm, false-blocking
         (missing valid trades) can be worse than false-permitting.

#4 — SL protection IOC hardcoded (MEDIUM — broker-specific)
  File: live/sl_protection.py, line 502
  Issue: Emergency close uses ORDER_FILLING_IOC. Some symbols on some
         brokers require ORDER_FILLING_FOK. Wrong fill type = rejected
         emergency close = unprotected position.
  Mitigation: FundedNext broker currently accepts IOC for all symbols.
         Would only break if changing brokers.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ✅ ORB detection (15-minute ORB, session-specific windows)
  ✅ Volatility contraction filter (40% compression threshold)

SECTION 7: EDGE DEGRADATION VECTORS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  These are factors that could DEGRADE the live edge vs backtest over time:

  1. SIGNAL REJECTION CASCADE (MEDIUM RISK)
     As account grows → position sizes increase → slippage increases →
     spread/R ratio increases → more signals rejected by guards →
     fewer trades → higher variance → more no-trade streaks.
     Impact: Becomes significant above $50K effective size.
     Mitigation: Guards are already conservative (30% spread/R).

  2. 10-SECOND POLLING BLINDSPOT (LOW RISK)
     Fast spikes (< 10 sec) trigger trailing in backtest but are missed
     in live. This means live trailing is BEHIND the backtest trailing.
     For 2.5R TP with 1R buffer trail: if a trade spikes to 2.3R in
     5 seconds then retraces, backtest would have trail at 1.3R (locks
     0.3R profit), but live doesn't see it.
     Impact: ~1-3% WR difference, ~$50-150/month on $6K account.
     Mitigation: Reduce polling to 5 seconds (CPU trade-off).

  3. NO-TRADE STREAK COMPOUNDING (CURRENT — 13 DAYS)
     Currently in a 13-day no-trade streak. The bot is functioning
     correctly — signals exist but are rejected by HTF trend filters
     (bearish HTF vs bullish ORB bias). This is NORMAL when the market
     is range-bound or mixed-trend.
     Impact: No edge degradation, but emotional pressure may lead to
     overrides that worsen results.
     Mitigation: None needed. Streaks of 7-14 days occur 2-3× per year
     in the 16yr backtest (max consecutive losses = 9).

  4. WEEKLY REPORT WAS NEVER FIRING (NOW FIXED)
     The weekly performance report was scheduled for Saturday when the
     bot was off. This meant there was NO weekly performance visibility
     for the entire live period.
     Impact: Missed early detection of per-symbol edge degradation.
     Now fixed: fires Friday 8 PM.

  5. ACCOUNT_RULES CRASH WAS SILENTLY HIDING (NOW FIXED)
     Every trade close was throwing a NameError that was caught by the
     main loop's error handler. This meant:
     - DD% was always 0 in the journal
     - The consecutive error counter was incrementing
     - After 5 trades close in quick succession → bot stops

     In practice, with max 2 trades/day and 10-second cycle periods,
     trades don't close in the same cycle, so the error counter would
     reset between closes. The bug was present but not triggering the
     5-error shutdown... yet.

SECTION 8: TRADE FLOW — COMPLETE SIGNAL-TO-EXIT PATH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Every 10 seconds, the bot runs this exact sequence:

  1. HEARTBEAT → write timestamp to live/logs/.heartbeat
  2. CONNECTION CHECK → reconnect if MT5/internet dropped
  3. DAILY RESET → at 5 PM EST (FundedNext day boundary):
     reset daily PnL, daily trades, trade_taken_today, DD daily baseline
  4. SCHEDULED REPORTS → check if daily (3 AM) or weekly (Fri 8 PM) due
  5. ACCOUNT + DD CHECK → update balance, check DD limits:
     - DD > 80% daily limit → Telegram warning (throttled 30min)
     - Daily DD breached → stop new trades (keep managing open)
     - Max DD breached → EMERGENCY CLOSE ALL + bot stop
  6. MARKET NOTIFICATIONS → detect open/close transitions, send recaps
  7. FOR EACH ACTIVE INDEX:
     a. _can_trade(symbol) → 12 pre-checks (see Section 2)
     b. If blocked → Telegram notification (throttled 10min, skip
        "market closed" and "already traded")
     c. If passed → _generate_signal(symbol):
        - Get 500 M1 bars from MT5
        - Compute session boundaries (DST-safe)
        - Get HTF trend (H1 20/50 EMA)
        - Call strategy.generate_signals() (ORB + filters + retest)
        - Stale signal guard (> 15 bars old → reject)
        - Price drift guard (> 0.5R from signal → reject)
        - Return signal dict or None
     d. If signal → _execute_signal(symbol, sig):
        - Position sizing (adaptive risk + free margin)
        - MIN R guard (< 3/5 pts → reject)
        - Random 1-2s delay (prop-firm avoidance)
        - Log expected price + spread
        - SPREAD-TO-R guard (> 30% of R → reject)
        - Place order (IOC, deviation=10)
        - POST-FILL risk guard (> 1.5× designed R → emergency close)
        - Track position, set trade_taken_today
        - Verify SL (3 retries, emergency close if fails)
        - Journal entry + Telegram notification
  8. _manage_positions() → for each tracked position:
     a. Closed externally? → query deal history, journal close,
        EdgeGuard record, Telegram
     b. Force close near session end? → close + journal + EdgeGuard
     c. SL missing (0.0)? → re-apply or emergency close
     d. BE trigger (≥ 1R profit)? → move SL to entry + 0.5×spread
     e. Trailing (after BE)? → trail with 1.0R buffer below MFE
  9. HOURLY STATUS → Telegram system status (throttled 1hr)
  10. 5-MIN STATUS LOG → balance, DD, active markets to log file
  11. SAVE STATE → persist to disk (power-off recovery)
  12. SLEEP 10 SECONDS
  
  ERROR HANDLING:
  - Any exception → increment consecutive_errors
  - Backoff: 30s → 60s → 120s → 240s → 480s (doubles each time)
  - After 5 consecutive errors → critical Telegram + bot stops
  - Watchdog detects the stopped bot within 30s → restarts it
